# Security

Document version: 2026-11-26 (minimal anonymous loopback Health endpoint; ADR0027).

## Supported Versions

Security fixes are provided for the latest published `1.0.x` release.

## Reporting a Vulnerability

Use GitHub's private security advisory reporting for this repository. Do not disclose secrets or exploitable details in a public issue. Receipt and remediation timing depend on severity and reproducibility.

## Security Model

The accepted target for Githubie/Buckettie is to trust applications authenticated as the same Windows owner, without per-application Issuer trust or Project-bound assertions. Owner authentication must still reject other users and unauthenticated HTTP; Provider Repository/branch policy, approval and audit remain. The Buckettie Consumer is implemented in source as explicit per-Provider windows_owner mode on verified user-host transport, with live version/contract/operation checks and no signature/token fallback. Githubie's owner Consumer, dedicated interoperability and explicit rollout remain pending; the normal installation has not switched modes. See [ADR0023](docs/adr/0023-same-user-provider-trust.md). Other Providers and local secret encryption are unchanged.

The design authority for Repository Provider authentication and local secret protection is the [Provider authentication specification](docs/specifications/Provider_Authentication_Specification.md). The development code defaults to per-operation ES256 assertions and fails closed until keys and Provider capabilities are configured. Native-platform and real-Provider rollout status is tracked in the [implementation receipt](docs/specifications/provider-authentication-transfer.md). Legacy repository authentication requires an explicit window of at most seven days. Existing service-token behavior below also serves lifecycle providers; it is not the new assertion protocol. External-service credentials remain owned by each Provider.

The MCP server binds only to loopback. GET `/health` exposes only status and the host version without authentication; see [ADR0027](docs/adr/0027-tray-mcp-server-health.md). All other HTTP requests require the current profile's 256-bit Bearer token. Missing, invalid and other-profile credentials receive HTTP 401. The token is generated by explicit initialization and stored only in `<INSTALLFOLDER>\config\moyai.json`, protected for the configured Windows owner, SYSTEM and Administrators; it is distinct from outbound Provider/service tokens. CLI client registration targets only the current Windows user's profile. Repository and lifecycle operations are delegated to configured providers. Service tokens are scoped by audience and scope and can expire, rotate, or be revoked. Release publishing and deployment require explicit target approval.

## Secrets Handling

Do not store service tokens in the repository, documentation, command examples, or logs. Pass secrets through the client or provider's supported secret mechanism. Token issuance and rotation return the plaintext secret once.

## User Responsibilities

The Windows MCP host runs under the logged-on user's identity. The sole operational configuration is `<INSTALLFOLDER>\config\moyai.json`, with one configured Windows owner. Database, logs, service tokens and CNG-protected secrets remain in that user's LocalAppData/profile scope; never import the legacy LocalService database or key automatically. Host control uses a local named pipe restricted to the current Windows user, while MCP HTTP remains loopback-only with its existing authorization checks. Review the exact active user and Provider target before mutations. Restrict file permissions, verify release SHA-256 files, and revoke credentials after suspected exposure.
