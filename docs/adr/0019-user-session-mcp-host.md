# ADR 0019: User-session MCP host and per-user state

## Status

Accepted 2026-10-22. Product owner approved preserving the legacy service DB/config/key and starting the user profile with a fresh DB and required Project/Provider re-registration. Implementation and local runtime/MSI validation are complete in the working tree; Windows acceptance and final delivery remain open.

## Context

The current `Moyai.Mcp.exe` is an ASP.NET Core host registered by the per-machine MSI as an automatic LocalService Windows Service. Its default config resolves under the installation tree; the database path is relative to that config. The installer grants broad user modification rights to the shared data and log directories. `moyaictl service` uses SCM APIs. `PausableServiceLifetime` maps SCM pause/continue to HTTP admission control. The host also creates and opens CNG keys under its process identity.

The requested model runs only in a logged-on user's session, provides a per-user logon-autostart toggle in a tray UI, keeps that setting distinct from the current host process state, and isolates DB, assertion keys, service tokens and logs per user. Existing projects may refer to different users' paths; service-token rows and audit records are in the shared DB, and secret envelopes depend on the old service identity's protector key.

## Decision

- Keep `Moyai.Mcp.exe` as the MCP server host and run it in the logged-on user's security context. Add a Windows tray controller as a separate user-facing component. The controller manages host start/stop/restart/status and a separate persisted autostart setting. Turning autostart off does not stop the current host; stopping the host does not turn autostart off.
- Replace LocalService/SCM lifecycle with user-session lifecycle. Use a per-user control channel restricted to the current Windows SID for management commands. Preserve loopback-only Streamable HTTP, API authorization, provider routing and in-flight request shutdown behavior. Keep CLI client operations in `moyaimcp`; use distinct commands for host process control and autostart configuration.
- Store the active user's config, DB and logs under that user's LocalAppData, inheriting the profile's user-scoped filesystem ACLs. Use an explicitly user-scoped CNG key and a user-specific assertion namespace. Choose and persist a loopback port per user so concurrent Windows logons do not contend for the current fixed port; refuse startup and report recovery steps if the persisted port is occupied.
- The per-machine MSI deploys binaries only. A user-context action initializes the current user's profile and enables its `HKCU` logon entry by default. Only product-owned startup values are changed or removed. A client profile belonging to another Windows identity must not be connected to this user's DB or endpoint.
- Do not automatically import the old shared service DB, tokens or CNG keys. Preserve the old config, DB and key material untouched as a rollback archive. Start each user's new DB without old records; require user-scoped project/provider re-registration. A future explicit importer may copy selected nonsecret project/work-item data after user ownership mapping; encrypted secrets and service tokens must be recreated or rotated. The new version must fail closed on per-user DB/key initialization errors and must never fall back to the old shared DB.
- Rollback reinstalls the previous service build and reuses its retained config/DB/key material. New user DBs remain separate and are not merged into the service DB during rollback.

## Alternatives

- Keep the existing LocalService host and grant interactive users access: rejected because it retains shared identity/state and cannot provide per-user secret isolation.
- Copy the shared DB and LocalService key to every user automatically: rejected because the DB has no owner mapping, contains shared service tokens and history, and the envelopes are bound to the old protector identity.
- Keep the Windows Service and add a tray-only setting UI: rejected because the host would still run in Session 0 and retain the service's permissions, contrary to the CR.
- Remove the host process controls and expose only a logon setting: rejected because the CR requires operations and documentation to distinguish autostart state from the running process.

## Impact and security

This changes the service lifetime contract, default config/data paths, host management commands, tray UI, MSI upgrade/uninstall behavior, logging, local endpoint selection, and user data ownership. Windows users must recreate projects/provider registrations in their new profile. Existing encrypted data cannot be read by the new identity without a separately designed and authorized migration. Retaining the original files permits rollback but does not make them visible to the new host.

The control channel must verify same-user access and reject remote clients. The product owner additionally approved per-user HTTP authentication on 2026-10-22: generate a random 256-bit token in each new profile; require a single matching Bearer header on every HTTP request; propagate it to CLI, Codex and Claude connections. Missing or invalid profile secrets prevent host startup; missing or foreign HTTP credentials return 401. Client setup must target the current Windows user's profile and ownership records store only token hashes. Per-user directories must not inherit broad Users write permissions. Secrets remain out of logs, command-line arguments and installer properties. The host must exit on logoff and run without elevated rights.

## Operations and migration failure behavior

On install/upgrade, stop and remove the old service through MSI sequencing, preserve its data/config/key material, create the current user's profile without overwriting an existing profile, and create the current-user autostart entry only after profile initialization succeeds. If profile creation or startup registration fails, fail the user-scoped setup and roll back only changes made by that transaction; never delete the legacy data. On runtime DB/key failure, do not start the HTTP listener and do not fall back to service-owned state. Uninstall removes only the product-owned autostart value and binaries; user DB/config/logs and the legacy rollback archive remain unless a later explicit data-removal operation is approved.

The 2026-10-24 host-control correction gives connection and response deadlines distinct cancellation sources. A connected peer that disconnects before a response is an error, not evidence that the host is stopped. The client writes request/ACK bytes directly to avoid a buffered writer flushing again after an acknowledged stop. CLI startup deadlines report a timeout with status-check guidance, while caller cancellation remains cancellation. Restart waits for the acknowledged process to exit (up to 15 seconds) before launching a replacement; an unconfirmed exit aborts restart. Isolated pipe and polling tests cover these boundaries; the installed candidate and broader Windows acceptance require separate verification.
